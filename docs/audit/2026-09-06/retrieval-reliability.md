# Retrieval reliability audit — sherlock-web @ 32c061f

Read-only code investigation. No server, no network. Offline probes run with `./venv/bin/python` (351 tests pass, 1 skipped). Third-party engines inspected in `venv/lib/python3.12/site-packages/` (sherlock-project 0.16.0, maigret 0.6.4, holehe 1.61, ignorant 1.2, scrapling 0.4.14, httpx 0.28.1). Line numbers are from the working tree; `SP/`, `MP/`, `HP/` abbreviate the sherlock_project / maigret / holehe package dirs.

**Headline.** The system is honest about *known* blockage (429/403/5xx, listed Cloudflare phrases, policy-denied hosts → `indeterminate` / `not_examined`), and the three-engine + adapter design gives real redundancy for *existence*. It is fragile in four places: (1) the third-party engines silently convert 429/challenge pages into `Available` or `Claimed` (never an error), so the router/circuit breaker cannot see most blocking; (2) verification's control-probe and marker lists turn *unlisted* WAF pages into "likely false positive" or "unconfirmed lead", and handle-echoing soft-404s into `confirmed 72`; (3) there is no per-host memory, throttle or backoff anywhere in the enrichment/adapter layer — a 429 triggers 2–3 *more* immediate requests to the same host; (4) per-run failure detail is never persisted, so a stored case cannot answer "what failed and why".

**Same real-world outcome, different labels (and where information is lost):**

1. **HTTP 429 on a profile host.** Sherlock: `Available` (status sites) or `Claimed` (message sites) — *success* to the router (`SP/sherlock.py:441-464`). Maigret: `Available`/`Claimed` likewise (`MP/checking.py:797-811`; `error_detection.py:30-35` only errors 403/5xx). WMN: `unknown`+"HTTP 429" → `http_429` (`whatsmyname.py:165`). Adapter: `blocked` → `indeterminate` (`adapters.py:123-126,327-330`). Enrichment: `indeterminate` "blocked: HTTP 429" (`verify.py:235-238`). Gravatar: `None` = "no profile" (`email_pivot.py:63-64`). Breach: `None` cached = silently omitted (`breach.py:109-111`). Brokers: `blocked`. Five labels; only WMN feeds the breaker.
2. **Cloudflare/WAF 200 interstitial.** Sherlock: `WAF` for 4 fingerprints else `Claimed` (`SP/sherlock.py:415-450`). Maigret: `Unknown`/"Bot protection error" for 20 substrings else `Claimed`/`Available` (`MP/errors.py:30-79`). WMN: `available` (string absent, `whatsmyname.py:113-115`). Enrichment: `indeterminate` for 15 phrases (`verify.py:80-86`) else `likely_false_positive` (control page identical, `verify.py:291-299`) or `unconfirmed` (`:319-323`). Router: `http_403_waf` only when engines say so. Three engine marker lists + two of ours (`stealthweb.py:88-104`, `verify.py:80-86`) are all different and none covers Akamai "Access Denied", Imperva "Pardon Our Interruption", AWS WAF, Kasada (verified offline: Akamai-style page → `likely_false_positive 10`; Imperva "Pardon" → `unconfirmed 45`).
3. **Policy-denied host.** Enrichment: `not_examined`/`access_policy` (`enrich.py:408-418`), UI "· not examined". WMN: `unknown` + "policy: …" → emitted as an **error row** (`pipeline.py:378-380`), classified `unknown` by the router (offline probe), counted in `error_breakdown.unknown`, buffered as a *failure* observation for the site (`router.py:602-614`) — 8 WMN sites (6 in the high-value subset) accrue fake failures every run. Sherlock/maigret: **not denied at all** — Instagram/Reddit/Twitter/Flickr/threads are in Sherlock's site list and are scanned each run (`app.py:146-148`, `pipeline.py:503`); `policy.py:14` ("denied hosts are never fetched") is true only of our own fetchers.
4. **Transport failure (DNS/TLS/timeout) in enrichment.** Exception type discarded at `enrich.py:246-247`; verify sees `status=None, html=None` → "no HTML retrieved — cannot determine existence" (`verify.py:239-242`). Same string for DNS-dead site, TLS reset, timeout, SSRF block (`safeweb.py:94-101`). Not logged. Not routed.
5. **Adapter `blocked` during discovery vs enrichment.** Discovery drops it silently (`adapters.py:297-298`, no error SSE, no observe); enrichment turns the *same* API answer into `indeterminate` (`adapters.py:327-330`).
6. **Control probe failed vs not applicable.** `probe = "ran" if control_html is not None else ("not_applicable" if html else None)` (`verify.py:227-228`): a control fetch that returned 429/timeout (`c_html None`) is reported as `control_probe: "not_applicable"` — indistinguishable from "URL did not contain the handle" (`enrich.py:250-256`). The failed control result is also cached for the host for the whole run (`enrich.py:391-400`).
7. **Detector ABSENT vs BLOCKED.** A 200 challenge/shell page without the present marker, after the ladder fails, is ABSENT (`detectors.py:89-90`) — the *absence of evidence* label, whereas the enrichment path labels the same page `indeterminate`.

## 6. Top 10 reliability defects (ranked by user impact)

1. **Soft-404 page that echoes the handle in `<title>` is CONFIRMED (score 72, confidence 75–90).**
   Symptom: not-found pages counted as verified accounts in headline/dossier (offline-reproduced, §3c).
   Root cause: `verify.py:304-307` (`_handle_in_metadata`) runs before the body soft-404 check (`:311-315`); `_SOFT_404` phrases (`:61-68`) require adjacency ("profile not found"); control similarity threshold 0.90 (`:53,295`) is defeated on short pages by handle substitution in the shingles.
   Smallest safe fix: in `verify_username`, before step 5, compute similarity after replacing both handles with a placeholder token (`text.replace(uname, "⟨h⟩")`, control likewise) and treat `sim ≥ 0.90` as FP; also add a regex soft-404 check `r"(profile|user|page|account)\b.{0,40}\b(not found|does ?n[o']t exist)"` on the headline.
   Test: `tests/test_verify.py` — page/control pair from §3c must yield `likely_false_positive`; the existing `test_confirmed_via_structured_metadata` must still pass.

2. **Unlisted WAF/anti-bot pages (Akamai, Imperva, AWS WAF, Kasada…) become "likely false positive" or "unconfirmed lead" instead of "blocked".**
   Symptom: blocked accounts shown as refuted (tier `refuted`, red) or as leads adding footprint points (offline-reproduced, §3b).
   Root cause: `verify.py:80-86` and `stealthweb.py:88-104` phrase lists; the control-probe rule (`verify.py:291-299`) fires on any identical page, including a block page; `should_escalate` (`stealthweb.py:142-158`) never triggers for these.
   Smallest safe fix: in step 4, if `sim ≥ 0.90` **and** the page lacks any profile-ish metadata (no `og:*`, no JSON-LD, title ≤ 4 words) return `indeterminate` "identical to control and carries no profile metadata — likely a block page"; extend both marker lists with `access denied`, `reference #`, `pardon our interruption`, `incapsula incident id`, `request unsuccessful`, `awswaf`, `kasada`, `<title>client challenge`.
   Test: `tests/test_verify.py` with the Akamai and Imperva bodies from §3b → `indeterminate`; `tests/test_stealthweb.py` → `should_escalate(200, akamai_html)` True.

3. **Third-party engines report 429/challenge pages as `Available`/`Claimed`, so the router and circuit breaker never see the dominant blocking mode.**
   Symptom: `/api/health/sources` shows healthy sites that are rate-limiting; silent false negatives (status_code sites) and false positives (message sites); WMN `available` on challenge pages.
   Root cause: `SP/sherlock.py:441-464` (no status≥400 branch except via 4 fingerprints `:415-420`); `MP/error_detection.py:30-35` (403/5xx only, no 429); `whatsmyname.py:113-115` (`status==e_code` without `e_string` → `available`).
   Smallest safe fix (our code only): in `whatsmyname.classify_response` return `UNKNOWN` with context `"HTTP 200 without e_string"` when `status_code == e_code` and body matches `stealthweb.has_challenge_markers` or `looks_like_shell`; for Sherlock/maigret, post-filter in `_SherlockNotify.update`/maigret `on_result`: if `results_raw[site]["http_status"]` ∈ {429, 403, 503} (available for sherlock via the returned dict `app.py:402-403`; maigret `results_info["http_status"]` `MP/checking.py:843`) re-label the observation as `http_429`/`http_403_waf` before `router.observe`.
   Test: `tests/test_whatsmyname.py` — 200 challenge body → `unknown`; router test that a synthetic sherlock result with `http_status 429` and status `Available` is observed as `http_429`.

4. **A 429 in enrichment triggers three more immediate requests to the same host and poisons the host's control probe for the run; nothing is remembered.**
   Symptom: cascading 429s across all rows of a host (name-candidate runs hit one host 20×); every subsequent row on that host loses soft-404 detection.
   Root cause: `enrich.py:458-459` escalates on any ≥400 (`stealthweb.py:150`) including 429; `escalate` `:361,371` back-to-back; `control_for` `:391-400` caches `(None/429, None, {})`; no per-host semaphore (`:31,343`); no `Retry-After` read; no router observe.
   Smallest safe fix: in `enrich.work`, if `status in (429, 503)`: skip the ladder, record `host_backoff[host] = now + Retry-After (default 60 s)`, and mark remaining rows on that host `indeterminate` with reason `rate_limited` without fetching; do not cache a control result whose status is None/≥400 (retry it once later or leave `control_probe` = `"failed"`).
   Test: `tests/test_enrich.py` — stub `_fetch_page` returning 429 for host A: assert exactly one fetch to A, no `fetch_tls` call, all A rows `indeterminate` with `reason == "rate_limited"`, control not cached.

5. **Watchlist emits false "account gone" alerts when a site is blocked or its circuit is open.**
   Symptom: analyst alerted that an account disappeared when the check was simply skipped or failed.
   Root cause: `monitor.py:122` removes open-circuit sites, `compute_signature` (`:155-165`) is built from found rows only, `diff_signatures` (`:186-193`) treats absence of a key as "gone"; light scan has no retry and no notion of "checked".
   Smallest safe fix: record the set of sites actually checked with a success-class result in the scan; in `diff_signatures`, emit `account_gone` only if the site is in `new_checked_ok`.
   Test: `tests/test_monitor.py` — old sig has `acct:github:x`, new scan skipped GitHub (degraded) → no alert; new scan checked GitHub and found nothing → alert.

6. **Email exposure claims "No registered-account exposure was found" when holehe was rate-limited or errored on every module.**
   Symptom: dossier/exposure score assert a negative that was never established.
   Root cause: `dossier.py:97,134-141`, `exposure.py:97,177`, `pipeline.py:463,689` count only `exists`; `rate_limit`/`error` entries are ignored in every aggregate (UI shows them per row, `app.js:1389,1452`).
   Smallest safe fix: compute `holehe_checked_ok = sum(1 for h if h.get("exists") is not None and not h.get("rate_limit"))`; if `holehe_hits == 0 and holehe_checked_ok < 0.5 * len(holehe)` write "email checks were rate-limited/failed on N of M services — exposure could not be determined"; add `email_rate_limited` to `done`.
   Test: `tests/test_exposure.py`/dossier test with 100 entries all `rate_limit: True` → text contains "could not be determined", score part for email = 0 and flagged as unknown.

7. **Per-run retrieval failures are not persisted; a stored case cannot explain what failed.**
